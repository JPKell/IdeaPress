# IdeaPress — Risk and Failure Analysis

Suite-wide risks: [Risk Register](../../architecture/risk-register.md).

---

## 1. Technical risks

| # | Risk | L | I | Mitigation | Early signal |
|---|---|---|---|---|---|
| T1 | **Model output treated as a decision** — a "looks good" response ending a gate | Medium | High | Gates are deterministic; five stages involve no model; a test asserts that a "stop, it's fine" response does not satisfy a gate | A gate passing with no deterministic evidence |
| T2 | **Unbounded revision** consuming hours without improving anything | High | Medium | Round limits; diminishing-returns stop computed from deterministic finding counts; "leave it alone" as a valid verdict; the stop reason recorded | Rounds consistently hitting the limit |
| T3 | **Context assembly errors** — dropping requirements to fit a budget | Medium | High | Requirements and unit specification are never droppable; documented reduction order; overflow fails with numbers | Units missing requirements they were assigned |
| T4 | **Validators too strict**, blocking legitimate content | Medium | Medium | Blocking/advisory split; thresholds are configuration; paused units surface the exact failing check | Units pausing frequently on the same check |
| T5 | **Validators too loose**, committing poor content | Medium | High | Deterministic checks plus requirement coverage; audit escalation; the coverage report shows which guarantees are mechanical | Committed units failing a later project review |
| T6 | **Requirement compiler fabricating constraints** | Medium | High | Anti-fabrication test with benign material; every requirement carries a source reference; compilation is a separate reviewable artefact | Requirements with no source reference |
| T7 | **Long-running stage lost** to a crash or a refresh | Medium | Medium | Persisted stage events with SSE replay; attempts marked `interrupted`; per-unit resumption; nothing partial is committed | Users re-running whole stages |
| T8 | **Export non-determinism** | Low | Medium | Deterministic rendering; byte-stability test across repeats and platforms | Diffs between two exports of the same project |
| T9 | **Backend abstraction leaking** provider specifics into workflow code | Medium | High | The port; adapters isolated; `LOADCOACH_TASK_MAP` in one module (asserted); import-linter | Workflow code importing `modelrack` or `httpx` |
| T10 | Project database growth with long histories | Low | Low | Content stored once per version; text storage opt-in; prunable attempts | — |

## 2. Integration risks

| # | Risk | L | I | Mitigation |
|---|---|---|---|---|
| I1 | LoadCoach API drift | Low | Medium | Version negotiation on first contact; schema-driven mock in tests; additive-only v1 |
| I2 | Accidental hard dependency on LoadCoach | Medium | High | Backend-parity test across three backends; import-linter; standalone e2e suite is the default CI path |
| I3 | Accidental dependency on FreeWeight | Low | High | Import-linter contract; the architecture gives IdeaPress no reason to talk to FreeWeight at all |
| I4 | LoadCoach queue delays surprising an interactive user | Medium | Low | Interactive class for user-facing stages; queue wait shown in the UI; `max_latency_seconds` |
| I5 | Different backends producing structurally different output | Medium | Medium | Parity test asserts identical structure; degradations recorded when a capability is missing |

## 3. Security risks

| # | Risk | L | I | Mitigation |
|---|---|---|---|---|
| S1 | **Model output rendered unsafely** (this is the application that renders the most model output) | Medium | High | Autoescaping; allowlist Markdown sanitizer; no `\|safe` on model content; tests with hostile payloads across every view and export format |
| S2 | Model output used to build a path or filename | Low | High | Never; unit and project identifiers are validated and generated by IdeaPress |
| S3 | Malicious project archive on import | Low | High | Hardened extraction: no absolute paths, no `..`, no symlinks, size and ratio caps, temp-directory staging |
| S4 | Private content leaving the machine via a remote backend | Medium | High | `allow_remote = false` by default; egress badge per stage in the UI; the backend page states plainly where content goes |
| S5 | Project content in logs | Medium | Medium | `include_content = false` by default; hashes only; redaction filter |
| S6 | LAN exposure of personal work | Low | High | Loopback default; tokens plus acknowledgement required; startup refusal |

## 4. Portability risks

| # | Risk | L | I | Mitigation |
|---|---|---|---|---|
| P1 | Windows/macOS users are IdeaPress's most likely audience | High | Low | No platform-specific code; `sweatmeter` optional; portable paths and encodings; non-blocking CI jobs on both platforms |
| P2 | Export rendering differing across platforms | Low | Medium | Byte-stability test in the CI matrix; explicit encodings and newline handling |

## 5. Performance risks

| # | Risk | L | I | Mitigation |
|---|---|---|---|---|
| F1 | Whole-project operations slow at 100+ units | Medium | Medium | Budgets asserted; per-unit streaming; indexed queries |
| F2 | Long documents held in memory repeatedly | Medium | Medium | Streamed exports; single-copy content handling; a large-project memory test |

## 6. Model risks

| # | Risk | L | I | Mitigation |
|---|---|---|---|---|
| M1 | Model refuses a legitimate creative task | Medium | Medium | `CONTENT_REJECTED` is a distinct outcome with the model's stated reason; the user can change model or rephrase; never scored as a failure of the workflow |
| M2 | Model produces plausible but wrong facts | High | High | Fact-check stage; citation validation for research-backed units; coverage report distinguishes mechanical from model-assisted guarantees; the product never claims factual accuracy it cannot check |
| M3 | Small models unable to hold enough context for a unit | Medium | Medium | Context budgeting with explicit failure; per-stage model bindings; LoadCoach's `min_context_tokens` constraint when available |
| M4 | Style drift across units | Medium | Low | Style constraints carried in every context; project review stage; glossary consistency validation |

## 7. Maintenance risks

| # | Risk | L | I | Mitigation |
|---|---|---|---|---|
| G1 | Workflow complexity outgrowing comprehension (the prior project's orchestrator reached 2 103 lines) | High | High | Stages as small, separately tested units; the state machine as data; no stage may exceed the module size guidance; the pipeline diagram is the specification |
| G2 | Content types leaking domain concepts into the engine | Medium | High | The engine knows units and requirements only; a term scan test for content-type vocabulary in engine modules |
| G3 | Prompt sprawl | Medium | Medium | Versioned records with mandatory change reasons; a prompt used by no stage fails a test |
| G4 | Export formats multiplying | Medium | Low | Shared rendering model; format-specific serializers only |

## 8. Deliberate trade-offs

* **Python owns control flow** — less "magic", more predictability, more code.
* **Deterministic gates first** — some quality dimensions are unmeasured rather than fake-measured.
* **Bounded loops** — occasionally stopping short of the best possible output rather than never
  stopping.
* **Committed units immutable** — more storage, but history that can be trusted.
* **Standalone first** — LoadCoach integration arrives late, guaranteeing independence is real.
* **No rich editor** — IdeaPress produces and validates; polishing prose by hand happens elsewhere.

## 9. Explicit non-goals (restated as risk control)

Benchmarking, routing algorithms, autonomous agents, publishing platforms, collaborative editing,
code execution. Each would either duplicate another component or dissolve the guarantee that Python
owns the control flow.

## 10. Premature optimizations to avoid

* A plugin system for stages before a second workflow needs one.
* Caching model outputs before repetition is observed to matter.
* A vector store for research before file-based notes are proven insufficient.
* Parallel unit generation before single-unit quality is solid (and while one GPU serializes it anyway).
* A generic template language before two content types actually diverge.

## 11. Architectural traps

* Letting a stage call a provider directly "just for this one case".
* Letting LoadCoach task IDs spread beyond the adapter.
* Letting an audit stage edit content.
* Letting a model choose the next unit or the retry budget.
* Treating advisory findings as blocking, or blocking findings as advisory, based on convenience.
